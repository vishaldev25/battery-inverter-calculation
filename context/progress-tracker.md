## Architecture Decisions
- **Frontend Typing:** Plain JavaScript with JSDoc, no TypeScript, per `code-standards.md`.
- **CSS Framework:** Tailwind v4, no `tailwind.config.js`, theme mapping via `src/index.css`.
- **Git Strategy:** Feature branch workflow; PRs into `main` trigger CodeRabbit review.
- **Backend Architecture:** Strict folder separation (`calculation/`, `projects/`, `catalog/`, `db/`, `csv/`, `report/`, etc.) per `code-standards.md`.
- **Database Driver:** `pymongo`'s `AsyncMongoClient`, fully async.
- **Calculation Engine (03-07, hardened and verified):** Pure, IEEE/NEC-formula-based, hard-error blocking. **Also returns audit-trail intermediate values** (`ah_autonomy`, `k_t`, `dod_max_used`, `eta_batt_used` from `battery.py`; `pf_avg_used`, `efficiency_used` from `inverter.py`; `cable_length_m`, `n_parallel_strings`, `i_fuse_computed_a` from `cabling.py`) alongside final results — **these now flow all the way through to the PDF report as of this session**, not just to `last_calculation_result`. Confirmed via direct trace of `_execute_pipeline()` that `MasterCalculationResponse.battery_summary`/`inverter_summary`/`cabling_summary` are unmodified pass-throughs of each module's own response dict — no relabeling happens at the API layer, so the calculation layer's field names are the same names the report layer (and any future dashboard) should read. **Protective device selection is standards-constrained**: `cabling.py` never returns a raw computed current as "the fuse rating" — it snaps to the nearest NEC 240.6(A) standard size via `select_standard_protective_device()`, hard-errors on NEC 240.4 coordination failure, and the PDF report now displays both the standard and raw computed value side-by-side for audit purposes.
- **Standards citation is chemistry-aware at the source AND now at the point of display:** `constants.py`'s `BATTERY_STANDARDS_BY_CHEMISTRY` is the single place that decides which standard applies to which chemistry (IEEE 485/1188 for lead-acid family, IEC 62619/63056 for LiFePO4). **As of this session, `pdf_builder.py` consumes this lookup directly** in its §3.2 Battery Bank Sizing block — no consumer should hardcode "per IEEE 485/1013" generically; they should look up this table instead, and the PDF is now the reference example of doing so correctly.
- **API Layer (08):** `/calculate` intentionally stateless; no DB access inside `backend/calculation/`.
- **Entrypoint (09):** Must run from project root; env-driven config.
- **DB Layer (10):** Single reused `AsyncMongoClient` via FastAPI `lifespan`; collection accessors only, no query logic.
- **Catalog Layer (11):** `matcher.py` performs Python-side filtering only, never computes sizing formulas. `BatteryCatalog`/`InverterCatalog` identify products via `make`/`model`, **not** a `name` field.
- **Projects Layer (12):** `repository.py` is pure data access, never raises on not-found. `_execute_pipeline()` extraction keeps stateless/stateful calculate paths provably identical — **confirmed this session, via direct trace, that this identical-path guarantee extends all the way to what gets persisted in `last_calculation_result` and therefore what the PDF report can read.**
- **CSV Layer (13):** Validates strictly against the real `LoadItem` — no parallel schema.
- **Queries Layer (14):** `queries.py` is read-only, mirrors `matcher.py`/`repository.py`'s data-access-only discipline.
- **Timestamp storage policy:** all backend-generated timestamps are stored as timezone-aware UTC via a small local `_utc_now()` helper in each file that needs it. Locale-specific display is explicitly a `frontend/` concern.
- **PF resolution policy:** `power_factor` on `LoadItem` is `Optional` — `None` means "resolve from `LOAD_CHARACTERISTICS[category]`," resolved in exactly one place (`load.py`'s `_resolve_power_factor()`). **No equivalent resolution policy exists yet for `surge_multiplier`.**
- **Route registration order (Feature 15):** any fixed-path route sharing a router with a `/{param}` route must be registered *before* the parameterized route.
- **CSV upload commit strategy (Feature 15):** strict all-or-nothing per-file validation, no partial commits, append-only via atomic `$push`.
- **Report Layer (16, and this session's follow-up):** `backend/report/pdf_builder.py` is pure formatting — reads `project`/`project.last_calculation_result` only, never calls into `backend/calculation/` directly (the one exception being a constants-only import of `BATTERY_STANDARDS_BY_CHEMISTRY` from `backend/calculation/constants.py`, which is static lookup data, not a formula or calculation call — consistent with Invariant 1, since no calculation function is invoked), never recalculates a single number. PDF is always fixed light-mode per `ui-context.md`. Chart implementation is ReportLab-native only. **Table cells must always be `Paragraph` objects, never raw strings** — this session's Cabling-table column addition followed this rule from the outset, but has not yet been visually re-verified (see Next Up) to confirm no new overflow was introduced by the added column.
- **Verification discipline reinforced (again, this session):** before writing any code to consume the audit's new fields, the user was asked to paste `router.py` rather than assuming the fields survive the pipeline's field assignments unchanged — consistent with `ai-workflow-rules.md`'s "paste real source files before code" standing rule, and this project's broader "verify, don't assume" discipline. The check confirmed the plan was correct with no surprises, but the check itself — not the absence of a surprise — is the discipline being reinforced. **Standing practice for any future visual-output feature (PDF, chart, etc.): render and visually inspect real output before calling a unit verified, not just review the code that generates it or confirm the source data reaches it correctly** — those are two separate verification steps (data-flow correctness vs. visual/layout correctness), and this session has completed only the first for the Cabling-table change.
- **External-critique triage discipline established:** when a third-party (including another AI) critique arrives, the first step is always to trace every specific number/claim back to its actual source (real engine output vs. test fixture vs. seed data) before deciding what to fix.
- **Smoke-test authoring discipline:** a smoke test's own calls into production code must be verified against real, currently-pasted source with the same rigor as production code itself.
